# v1.5.0 — Native Antigravity CLI Execution Bridge

**Release date**: 2026-08-30
**Task**: HARNESS-0021
**Status**: `completed_with_deviation`
**Acceptance**: `passed_with_deviation`

---

## Summary

v1.5.0 introduces the Native Antigravity CLI Execution Bridge — the physical
execution layer that allows the Harness to invoke `agy` (Google Antigravity CLI)
in real subprocesses, fully sandboxed and governed.

This release enables governed autonomous physical execution for two workflow
modes:

- **`plan-task`**: Uses a Staging Sandbox for Task Contract drafting.
- **`implement-task`**: Uses a Git Worktree Sandbox for isolated mutations with
  full diff validation and scope enforcement before any changes reach the
  official repository.

> **All other workflows** (`discuss`, `approve-task`, `review-task`,
> `security-review`, `document-task`, etc.) **remain blocked** for autonomous
> physical execution. The Runner pauses immediately with a governed reason when
> these are routed. Physical execution for additional workflows will be enabled
> in future releases.

---

## New Components

### AntigravityCliExecutor
Official bridge that invokes `agy` in a subprocess with `--output-format json`.
Features:
- Configurable timeout
- Robust JSON response parsing
- Command injection prevention
- Structured output with conversation ID, duration, usage metrics

### StagingSandbox
Temporary directory for `plan-task` operations. Generated Task Contract drafts
are validated by the Harness before being copied to the official `projects/`
directory.

### WorktreeSandbox
Git worktree-based sandbox for `implement-task` operations. Creates an isolated
worktree branched from a baseline commit. All mutations occur inside the
worktree — the official repository is never directly modified by the executor.

### SandboxChange
Dataclass preserving Git operation semantics:
- `A` — file created
- `M` — file modified
- `D` — file deleted
- `R` — file renamed (preserves `old_path`)

`apply_to_main()` enforces operation-specific semantics: copies for A/M, unlinks
for D, unlink+copy for R. Deletions are never inferred from file absence —
only explicit `D` status triggers deletion.

---

## Scope Enforcement

The Harness validates every diff produced in the sandbox against the Task
Contract's `scope.planned_paths.modify` before any changes reach the official
repository.

- Each changed file path must appear in the approved scope.
- For renames, both `old_path` and `path` are validated.
- Task Contract YAML files within `projects/*/tasks/*.yaml` are always excluded
  from scope checks (governance files).
- Out-of-scope files → immediate rejection, no `validated`, no `applied`.
- Empty diff when modifications were expected → immediate rejection.

This enforcement (Layer B) operates at the filesystem/Git level and does not
depend on the LLM's self-policing behavior.

---

## Workflow Mode Classification

Autonomous execution is restricted to authorized workflow modes:

| Mode | Workflows | Sandbox | Executor |
|------|-----------|---------|----------|
| Planning | `plan-task` | `StagingSandbox` | Yes |
| Mutational | `implement-task` | `WorktreeSandbox` | Yes |
| Blocked | All others | None | No |

Blocked workflows produce an immediate `paused` with reason:
`"Workflow '{name}' is not enabled for autonomous physical execution."`

---

## Governed Pause After Implementation

After `implement-task → applied`, the Runner emits:

```
status='paused'
reason='Implementation applied. Awaiting governed review.'
```

and stops. There is no second iteration, no `discuss` fallback, and `max_steps`
is never the normal exit condition for a successful implementation.

---

## Human Gates

The Runner checks Task Contract status before every execution step:
- `awaiting_approval` → paused
- `approval_status: pending` → paused
- `acceptance_status: pending` after completion → paused
- Escalation keywords in user input → paused

---

## Task Contract Propagation

When using `WorktreeSandbox`, untracked Task Contract files from the main
repository are copied into the worktree before executor dispatch. This ensures
the executor can read and respect the contract inside the sandbox.

## Evidence

### E2E Phase 1 — Planning
Real `agy` invocation via `AntigravityCliExecutor` producing a Task Contract
in `StagingSandbox`, followed by `Human Gate: Task is awaiting_approval`.

### E2E Phase 2 — Implementation
Real `agy` invocation producing physical file `e2e_contador.html` in a Git
worktree. Full lifecycle: `planned → sandbox_created → dispatched → executed →
validated → applied → paused` (governed review). Single agy execution, no
Step 2 discuss, no max_steps exit.

### Deterministic Scope Enforcement
`test_worktree_scope_integration.py` — three tests using real Git repos and
real worktrees proving that rogue files created by an executor are detected by
`get_diff()`, rejected by scope validation, and never reach the main repository.
These tests do not depend on LLM behavior.

## Accepted Deviations

### Deviation 1: AutonomousRunner modifications
`adapters/antigravity/autonomous_runner.py` was originally listed as read-only
in the scope. Sandbox lifecycle was centralized in the Runner instead of the
Orchestrator to unify audit trailing and avoid mixing Antigravity-specific
execution states into universal Orchestrator logic.

### Deviation 2: Canonical project key support
`adapters/antigravity/adapter.py`, `engine/context/loader.py`,
`tests/test_antigravity_adapter.py`, `tests/test_context_loader.py` were not
in the originally approved scope. They were modified to support the
`.harness-internal` canonical project key with path traversal protection
(regex `^[a-zA-Z0-9_.-]+$` with explicit `..` blocking).

Both deviations were documented, authorized, and accepted by Yhoanes.
