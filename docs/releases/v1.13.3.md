# HARNESS v1.13.3

Tema: Runner Exit-Code Semantics

## Bug

engine.runner anteriormente podía producir:
ExecutionResult.status == FAILED
pero process exit code: 0

Esto hacía que shells, CI/CD y automatizaciones interpretaran una ejecución gobernada fallida como éxito operacional.

## New CLI contract

Provider:
- COMPLETED = 0
- FAILED = 11
- BLOCKED = 12
- INCOMPLETE = 13
- CANCELLED = 14
- UNKNOWN = 20

Legacy:
- completed = 0
- failed = 11
- paused = 12
- incomplete = 13
- empty trail = 13
- unknown = 20

Aclarar:
- provider y legacy no poseen modelos de estado idénticos;
- los mappings se mantienen explícitamente separados;
- unknown falla cerrado;
- process exit code complementa ExecutionResult, no lo reemplaza.

## Architecture

main() ahora devuelve int.

La frontera executable convierte ese resultado a process exit semantics.
Actualmente puede usar:
sys.exit(main())
que es funcionalmente equivalente a:
aise SystemExit(main())
en esta frontera.

## Exceptions

Uncaught internal exceptions NO se convierten artificialmente en governed FAILED.
Siguen propagándose con traceback y proceso non-zero.

## Compatibility

Es PATCH porque corrige un comportamiento CLI defectuoso.
Sin embargo es observable:
FAILED:
antes podía retornar 0;
ahora retorna 11.

Automatizaciones que dependían del falso éxito cambiarán comportamiento intencionalmente.

## Programmatic APIs

No cambios en:
- ExecutionResult
- ExecutionStatus
- HarnessEngine
- ExecutionProvider
- AntigravityExecutionProvider
